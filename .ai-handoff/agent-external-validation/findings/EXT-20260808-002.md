- Classification: `product_failure`
- Suspected root owner: `semantic_planning`
- Supporting evidence: turn-3 response (session.log L79) successfully answers
  "请列出支持的所有链名称" with the full 36-chain configured list, proving
  the chain registry is loaded and queryable. Turn-6 response (L129) after
  `use solana` returns the real workload template with weights, proving the
  workload-template renderer works when chain context is bound. The gap is in
  turn 4: the query "什么是 solana 的默认 RPC workload?" contains all
  information required to bind the chain, but the semantic_planning layer
  did not extract it into `chain_context` before dispatching to the workload
  renderer. Two plausible mechanisms: (i) intent parser recognizes
  workload-query intent but its slot extractor does not run chain-name NER on
  the utterance; (ii) intent parser recognizes intent and slot but response
  authority requires chain to be bound in session state (not turn-local
  extraction) and silently falls through.
- Evidence against stale session/data contamination: session started fresh
  in the container at 2026-08-08 16:28 UTC; session.log begins with startup
  diagnostics (L1-L26) showing clean cold-start; no prior `.agent/` state on
  this container; session-state.json before turn 4 had no chain bound (only
  language field). Turn-6 success on the same session proves the workload
  renderer is not broken by any stale data.
- Not tested because: adjacent variants ("show me the workload for arbitrum",

  captured 6 turns then closed. Codex should include ≥2 chain-name variants
  and ≥2 phrasing variants in reproduction to confirm the auto-extract gap
  is general and not a solana-specific parse failure.
